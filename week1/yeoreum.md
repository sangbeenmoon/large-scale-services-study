## 핵심 내용 요약

데이터가 커지면 병목의 성격이 달라진다. 따라서 부하의 원인을 구체적으로 측정하고

그에 맞게 시스템 구성과 데이터 처리 방식을 바꿔야 한다.
 
#### **1. 서비스가 성장하면서 어려워지는 것들**

| 과제 | 필요한 대응 |
| --- | --- |
| **확장성과 부하분산** | 한 서버의 처리 한계를 넘으면 요청과 역할을 분산해야 한다. 이 과정에서 데이터 동기화와 네트워크 지연 등의 새로운 문제가 생긴다. |
| **다중성 확보** | 일부 서버가 고장 나더라도 서비스를 계속할 수 있는 구성이 필요하다. |
| **효율적인 운영** | 서버가 많아질수록 사람이 일일이 관리하기 어려워지므로 모니터링, 정보관리, 자동화가 필요하다. |
| **개발 조직의 변화** | 여러 사람이 협업할 수 있도록 개발 방식의 표준화, 코드 리뷰, 작업 이력 공유가 필요하다. |
| **대규모 데이터 처리** | 메모리에서 처리하지 못하는 데이터가 늘어나면 디스크 접근으로 인한 성능 저하에 대응해야 한다. |

#### 2. 처리 성능을 올리는 방법

> **서버 대수를 늘리거나 역할을 나누는 스케일아웃**과 **개별 서버의 하드웨어 성능을 높이는 스케일업**이 있다.   
> 여기에 장애가 발생해도 서비스를 유지하기 위한 다중성 확보가 함께 필요하다.
>

#### 3. **데이터가 커지면 왜 느려지는가?**

데이터 증가에는 두 가지 비용이 따른다.

- 처리해야 할 데이터가 많아져 계산량이 증가한다.
- 메모리에서 처리하지 못하는 데이터가 늘어나 느린 디스크에 접근하게 된다.

## 인상 깊은 내용

> 특히 기억에 남거나 공감된 부분
>

#### 1. 모든 문제를 미리 예측할 수는 없다

대규모 트래픽으로 인한 문제는 직접 겪어보기 전까지 구체적으로 상상하기 어렵다.

실제 운영에서는 기존 지식만으로 바로 해결할 수 없는 미지의 문제도 발생한다.

그래서 **기본 원리를 이해해두고, 문제가 발생하면 그 상황에서 생각하자**는 관점

#### 2. 대규모 데이터를 다루기 위한 세 가지 방향

1. **최대한 메모리에서 처리를 마친다.** (캐시 등을 총해 디스크 접근 횟수를 줄인다)
2. **데이터량 증가에 강한 알고리즘과 자료구조를 사용한다.**
    - 예시: 선형검색O(n) 대신 이분검색O(log n)을 사용해서, 매번 전체데이터를 훑는 과정을 줄인다.
3. **데이터 압축과 검색엔진을 활용한다.**
    - 데이터를 압축하면 디스크 조회 횟수를 줄일 수 있다.
    - 특정 용도의 검색엔진을 만들고, 웹 애플리케이션에서 사용하면 속도 확보 가능

#### 3. 성능 개선을 위해 원인을 추적하는 흐름

> **전체 부하 확인 → 원인 범위 축소 → 병목 확인 → 개선** 순서로 접근
>
1. Load Average로 전체 부하 상황을 확인한다.
2. CPU 사용률과 I/O 관련 지표로 원인을 좁힌다.
3. 메모리 부족, 스왑, 개별 프로세스 등을 추가로 살핀다.
4. 확인한 병목에 맞춰 프로그램 개선, 메모리 증설, 캐시, 분산 등을 검토한다.

## 이해가 어려웠던 내용

**Load Average**

- 서버에 일이 얼마나 몰려 있는지 나타내는 지표
- 1분·5분·15분 단위의 평균 시간당
    - 현재 실행 중이거나 CPU 차례를 기다리는 작업
    - 디스크 I/O 등으로 대기 상태에 있는 작업
- 값이 높다고 CPU 부족이라고 단정할 수는 없고,

  종합적인 수치이므로 값이 높은 경우 CPU 개수와 I/O 대기 상황을 함께 봐야 한다.


## 의문이 드는 내용

- `%iowait` 비율을 보고 판단하는데, 구체적으로 어느 정도의 수치를 병목이라고 판단하는지?
- 고정된 병목 기준이 있는가?



%iowait은 **디스크 사용률이 아니라 CPU 시간에 관한 지표**여서  
CPU 개수와 다른 작업의 실행 상황에 영향을 받는다.  
이 값만으로 판단하는 데 한계가 있고 실제로는 다음을 함께 확인한다.


| 확인할 것 | 의심할 만한 변화 |
| --- | --- |
| **`%iowait`** | 평소보다 높은 상태가 지속됨 |
| **서비스 응답 시간** | 같은 시간대에 응답이 느려짐 |
| **디스크 I/O 처리 시간** | 요청 하나를 처리하는 시간이 길어짐 |
| **디스크 대기열** | 처리하지 못한 요청이 쌓임 |
- **예를들어 평소 1%였던 값이 20%로 올라가 계속 유지되고**
- **디스크 처리 시간이 늘면서 서비스도 느려진다면** I/O 병목을 강하게 의심할 수 있다.
